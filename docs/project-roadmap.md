# OpsPilot 项目总纲与路线图

## 1. 这是什么项目

OpsPilot 是一个面向 Go HTTP 微服务研发和运维场景的**证据驱动故障诊断助手**。

它的目标不是替人直接修改生产系统，也不是把模型包装成一个“万能聊天机器人”，而是帮助开发者把一次模糊的故障描述，逐步整理成：

```text
故障现象
  → 补充上下文
  → 收集可授权的证据
  → 形成带引用的假设
  → 给出验证步骤
  → 在人工确认后执行有限动作
```

项目默认只读。当证据不足时，工具应该明确说“还不知道”，而不是把模型猜测包装成事实；涉及重启、扩容、回滚、改配置等高风险动作时，必须经过人工确认。

## 2. 最终希望产出什么工具

最终产出是一个面向 Go HTTP 微服务的研发故障诊断工作台，包含以下核心能力：

### 2.1 输入故障上下文

用户可以提供：

- 自然语言故障现象；
- 服务名称、版本和运行环境；
- 日志、指标、trace 和 pprof 摘要；
- Git 变更记录；
- Runbook 和历史事故资料；
- 用户明确授权的只读查询结果。

### 2.2 输出结构化诊断

工具输出不应只是自然语言段落，而应逐步形成结构化结果：

- 现象摘要；
- 影响范围；
- 可能原因和置信度；
- 支撑每个判断的证据引用；
- 当前信息缺口；
- 建议的验证步骤；
- 风险和回滚提示；
- 可选的人工确认动作。

### 2.3 保留可复查过程

每次诊断应该能够复查：

- 用户提供了什么信息；
- 工具读取了哪些证据；
- 使用了哪个模型和 Prompt 版本；
- 模型返回了什么 usage；
- 诊断结论引用了哪些材料；
- 哪些动作被建议、确认、拒绝或执行。

### 2.4 支持不同使用入口

产品形态按阶段演进：

```text
本地 CLI
  → 可复查的诊断会话
  → HTTP API
  → React 诊断工作台
```

CLI 是学习和验证核心链路的起点，不是最终产品形态。最终工具应让研发、测试和运维人员能够在一个界面中提交上下文、查看证据、跟踪诊断过程并进行人工确认。

## 3. 产品边界

### 3.1 解决的问题

- 故障信息分散，排查过程缺少结构；
- 初步猜测没有证据支撑；
- 排查步骤依赖个人经验，难以复用；
- 模型回答没有记录，事后无法复盘；
- 自动化工具容易越过权限和人工确认边界。

### 3.2 不解决的问题

- 不承诺自动发现所有生产故障；
- 不替代监控、日志、trace、APM 或事件平台；
- 不在没有授权时读取生产系统；
- 不默认执行高风险变更；
- 不把模型输出当作最终事故结论；
- 不在早期阶段追求“大而全”的 Agent 自主性。

## 4. 总体架构演进

项目按能力依赖关系逐层建设：

```text
┌──────────────────────────────────────────────┐
│ v1.0 React 诊断工作台、权限、部署与运维         │
├──────────────────────────────────────────────┤
│ v0.7 MCP 对外开放被授权的诊断能力               │
├──────────────────────────────────────────────┤
│ v0.6 HTTP 服务、可靠性、成本、安全、观测         │
├──────────────────────────────────────────────┤
│ v0.5 Agent 工作流、只读证据收集、审计            │
├──────────────────────────────────────────────┤
│ v0.4 RAG：Runbook、历史事故、引用和拒答          │
├──────────────────────────────────────────────┤
│ v0.3 Provider 抽象、本地/云端路由和降级           │
├──────────────────────────────────────────────┤
│ v0.2 Prompt 版本、诊断 Schema、回归样本           │
├──────────────────────────────────────────────┤
│ v0.1 可测试 Go CLI：单次、多轮、流式、会话证据    │
└──────────────────────────────────────────────┘
```

底层版本先解决“能不能稳定调用和记录”，中间版本解决“能不能基于证据诊断”，上层版本解决“能不能安全地服务多人和长期运行”。

## 5. 项目总链路：从学习主线到商业产品

OpsPilot 同时承担两个目标：一是作为 AI 应用开发的长期实践项目，完整跑通从模型调用到 Agent、MCP 和产品化的工程链路；二是围绕一个明确的故障诊断场景，逐步验证真实用户价值，最终形成可独立交付的产品。

这两个目标不冲突，但不能采用“两套完全不同的系统”分别实现。正确做法是：**学习通用技术，产品聚焦垂直场景；学习阶段允许简化基础设施，但不牺牲领域边界、证据约束和安全原则。**

### 5.1 一条完整的能力链路

项目按下面的顺序逐层演进：

```text
明确目标用户和故障场景
  → 建立故障诊断领域模型
  → 接收故障描述和静态证据
  → 调用模型完成基础分析
  → 通过 Prompt 约束诊断行为
  → 输出并校验结构化诊断结果
  → 记录会话、usage、Prompt 和错误
  → 接入可替换的模型 Provider
  → 导入 Runbook 和历史事故资料
  → 检索相关知识并保留引用
  → Agent 规划有限的诊断步骤
  → 通过受控工具收集动态证据
  → 使用 MCP 连接外部系统或开放能力
  → 通过 HTTP API 提供服务
  → 建设权限、审计、观测和成本治理
  → 通过 React 工作台服务团队用户
  → 验证留存、复用和付费意愿
```

每一层都要回答两个问题：

1. 这一步学习了什么 AI 应用开发能力？
2. 这一步为故障诊断用户减少了什么成本或风险？

如果只能回答第一个问题，它是技术练习；如果只能回答第二个问题，它可能是产品功能，但未必能形成可迁移的工程能力；能够同时回答两个问题，才是本项目优先实现的内容。

### 5.2 学习主线与产品主线

| 主线 | 核心目标 | 主要验收方式 |
|---|---|---|
| AI 应用学习主线 | 掌握 LLM、Prompt、结构化输出、RAG、Agent、MCP 和 AI 工程化 | 可运行代码、测试、实践证据和技术笔记 |
| 商业产品主线 | 找到一个可重复、可信赖且有人愿意持续使用的诊断场景 | 用户反馈、真实案例、使用留存和付费验证 |

学习主线按照技术依赖推进，产品主线按照用户价值推进。两条主线在“证据驱动的故障诊断”这个领域模型上汇合，而不是让每一个学习主题都直接变成一个产品功能。

### 5.3 产品化的最小切口

在没有完成用户验证前，产品不追求覆盖所有运维问题。第一阶段的商业假设限定为：

> 面向使用 Go HTTP 微服务的研发、测试和 SRE 团队，帮助他们更快完成接口延迟、错误率、CPU、内存、goroutine、GC、数据库连接池和下游依赖等问题的证据整理与初步诊断。

优先交付“人工提供证据，系统生成可复查诊断报告”的辅助模式，再逐步自动接入监控、日志、Kubernetes、pprof 和 Git。这样可以先验证诊断结果是否有价值，再投入高成本的 Agent 自动化和生产系统集成。

### 5.4 每个版本的双重验收

每个版本完成时，同时检查技术门槛和产品闸门：

| 技术门槛 | 产品闸门 |
|---|---|
| 功能实现正确，失败路径可控 | 用户问题是否被更快、更清晰地处理 |
| 关键行为有测试和回归样本 | 结果是否比普通聊天更容易信任和复查 |
| 模块边界支持后续替换 | 是否围绕一个明确场景，而不是无限扩张 |
| 关键数据有记录和审计 | 是否减少重复排查、经验查找或协作成本 |

产品闸门连续两次无法通过时，应暂停扩展技术范围，回到用户访谈、真实案例和场景收敛，而不是继续增加 Agent、工具或模型能力。

### 5.5 不同阶段的产品形态

产品形态不需要一次完成，而是按用户价值逐步升级：

```text
v0.1：个人 CLI 诊断记录
  → v0.2：稳定的结构化诊断报告
  → v0.3：可按隐私、成本和能力选择模型
  → v0.4：结合团队 Runbook 和历史事故进行诊断
  → v0.5：自动执行有限的只读证据收集
  → v0.6：多人可使用的后端服务
  → v0.7：通过 MCP 安全连接和开放诊断能力
  → v0.8：沉淀可复用的领域排障 Skill
  → v1.0：面向团队的 SaaS 或私有化工作台
```

这里的“学习完成”不等于“产品完成”。例如，完成 MCP 只证明掌握了一种能力开放机制；只有当 MCP 连接真实的日志、指标或部署系统，并且在权限和审计边界内减少了排障成本时，才证明了产品价值。

### 5.6 当前阶段的执行原则

- 先完成 `v0.1` 基础工程闭环，再进入 `v0.2` 结构化输出，不提前堆叠 Agent 和 MCP。
- 从 `v0.2` 开始同步收集真实故障样本和用户反馈，不等到 `v1.0` 才验证商业方向。
- `v0.4` 之前优先验证“诊断报告是否有用”，`v0.4` 之后再验证“自动取证是否有用”。
- 通用 Agent 可以作为对照组；每个产品功能都要说明相比直接使用 Codex 或 ChatGPT 的增量价值。
- 复杂基础设施可以后置，但领域对象、证据引用、权限边界、错误分类和审计接口要提前设计。

## 6. 分阶段路线图

### v0.1：建立可复查的故障分析 CLI

**阶段目标：** 证明一条最小但完整的模型调用和诊断会话链路。

**主要交付：**

- Go CLI 项目骨架；
- OpenAI 兼容模型端点；
- 单次非流式调用；
- 进程内多轮会话；
- SSE 流式输出；
- 上下文取消和资源释放；
- usage 记录；
- 脱敏会话保存；
- 配置、网络、HTTP、协议和取消错误分类；
- 测试、证据和 v0.1 复盘。

**阶段不做：** RAG、Agent、MCP、自动修复、生产级服务和前端工作台。

**完成门槛：** 用户可以运行 CLI 完成一次多轮故障分析，退出后能够查看脱敏记录，失败路径有测试，验证结果可复查。

对应项目单元：`M1-P01`、`M1-P02`、`M1-P03`。

### v0.2：Prompt 与结构化输出

**阶段目标：** 让诊断结果从自由文本变成稳定、可测试、可演进的数据结构。

**主要交付：**

- 诊断结果 Schema；
- 现象、假设、证据缺口、验证步骤和风险字段；
- Prompt 版本号和变更记录；
- 结构化输出解析和校验；
- 非法结构、字段缺失和模型拒答处理；
- 固定回归样本集；
- Prompt 版本之间的结果对比；
- 结构化结果与自然语言展示的分离。

**阶段不做：** 不引入知识库检索，不让模型直接执行外部动作。

**完成门槛：** 同一组回归样本可以重复验证 Schema 和 Prompt 变化；结构化结果失败时不会静默当作成功。

### v0.3：Provider 抽象与模型路由

**阶段目标：** 在不修改诊断业务层的前提下支持不同模型来源。

**主要交付：**

- 统一 Provider 接口；
- OpenAI 兼容云端 Provider；
- 本地模型 Provider；
- 云端、本地和备用 Provider 路由；
- 能力声明，例如是否支持流式、结构化输出和 usage；
- 超时、降级和不可用 Provider 的明确策略；
- Provider 级别的测试矩阵。

**阶段不做：** 不在路由层隐藏不可控的自动重试，不因为“支持更多模型”而牺牲错误透明度。

**完成门槛：** 更换 Provider 不需要修改 `internal/app` 的诊断编排，能力不匹配会得到明确错误。

### v0.4：RAG 与证据引用

**阶段目标：** 让诊断建立在项目 Runbook、历史事故和工程资料之上。

**主要交付：**

- Runbook 导入与切分；
- 历史事故样本索引；
- 文档版本和来源管理；
- 检索结果与引用片段；
- 诊断结论到证据的映射；
- 没有足够相关资料时的拒答；
- 检索质量和引用正确性的评估样本。

**阶段不做：** 不把检索到的文档内容直接当作事实，不绕过权限读取任意资料。

**完成门槛：** 每个重要判断都可以追溯到用户输入、运行证据或知识库引用；证据不足时明确拒答或降级为假设。

### v0.5：Agent 与只读工作流

**阶段目标：** 让工具能够按照有限、可审计的步骤收集诊断证据。

**主要交付：**

- 有限状态的诊断工作流；
- 只读工具调用；
- 证据收集步骤和超时；
- 步骤预算、循环上限和取消；
- 每一步的输入、输出和错误审计；
- 人工确认节点；
- 失败后可恢复或安全终止。

**阶段不做：** 不允许无边界自主循环，不默认执行生产变更。

**完成门槛：** Agent 的每一步都可解释、可取消、可限制、可审计，且不会因为工具异常进入无限循环。

### v0.6：AI 应用工程化

**阶段目标：** 将核心能力变成可以被团队稳定使用的后端服务。

**主要交付：**

- HTTP API；
- 会话和任务管理；
- 身份认证与授权；
- 并发控制、超时、限流和重试策略；
- 成本和 usage 观测；
- 结构化日志、指标和 trace；
- 敏感信息处理与审计；
- 数据保留、删除和故障恢复策略；
- 部署和运维说明。

**阶段不做：** 不为了追求自动化而放宽权限和审计边界。

**完成门槛：** 服务可以在受控环境中稳定运行，出现模型、网络、工具或存储故障时能够定位、降级和恢复。

### v0.7：MCP 能力开放

**阶段目标：** 以明确授权的方式对外提供诊断能力。

**主要交付：**

- MCP Server 能力边界；
- 工具和资源描述；
- 输入校验；
- 授权、租户隔离和审计；
- 只读能力默认策略；
- 高风险操作的人审确认；
- MCP 客户端兼容性测试。

**完成门槛：** 外部调用方只能访问被授权的能力，所有调用都有身份、参数、结果和审计记录。

### v0.8：Skill 化领域能力

**阶段目标：** 把经过验证的排障经验沉淀为可测试、可组合的领域能力。

**主要交付：**

- Go HTTP 延迟排查 Skill；
- CPU、内存、goroutine 和锁竞争排查 Skill；
- 数据库连接池和下游依赖排查 Skill；
- 输入、证据、输出和失败条件定义；
- Skill 版本和回归样本；
- Skill 与 RAG、Agent 工作流的组合方式。

**完成门槛：** Skill 不是一段 Prompt，而是有明确输入输出、证据要求、边界和自动化测试的能力单元。

### v1.0：产品化诊断工作台

**阶段目标：** 形成面向真实团队使用的 React + Go 产品。

**主要交付：**

- React 诊断工作台；
- 会话、任务和证据时间线；
- 诊断结果、引用和信息缺口视图；
- 多用户、团队和权限；
- Provider、Prompt 和 Skill 管理；
- 人工确认与操作审计；
- 部署、升级、备份和运维；
- 用户文档、开发文档和安全说明。

**完成门槛：** 团队成员可以在权限边界内完成“提交故障 → 补充证据 → 查看诊断 → 人工确认 → 复盘记录”的完整闭环。

## 7. 阶段之间的依赖关系

每个阶段都应该建立在前一阶段可验证的能力之上：

```text
v0.1 稳定调用和记录
  → v0.2 稳定输出格式
  → v0.3 可替换模型来源
  → v0.4 可引用工程知识
  → v0.5 可控地收集外部证据
  → v0.6 可长期运行和观测
  → v0.7 可安全开放能力
  → v0.8 可复用领域经验
  → v1.0 面向团队产品化
```

如果底层没有稳定的错误、会话和证据记录，上层的 Agent 和前端只会把不稳定性包装得更复杂。因此每次升级都要先检查上一阶段的验收和回归是否仍然成立。

## 8. 每个阶段的统一交付物

任何版本完成时，至少需要同时交付：

1. **代码**：功能实现和清晰的模块边界；
2. **测试**：正常路径、失败路径和关键边界；
3. **证据**：环境、命令、结果和已知限制；
4. **文档**：里程碑、README、技术笔记和必要的 ADR；
5. **复盘**：这次证明了什么、没有证明什么、下一阶段依赖什么。

不能只因为“功能可以运行”就宣布一个阶段完成。阶段完成意味着代码、测试、证据和边界说明形成闭环。
