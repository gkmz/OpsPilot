# M1-P02：多轮与流式诊断

## 目标

在现有单次非流式 CLI 的基础上，支持同一会话中的多轮故障补充信息和流式增量输出，并保证取消、断流和错误场景不会污染会话状态。

## 当前基线

- `internal/app` 负责组装配置、模型客户端和 CLI 用例。
- `internal/llm` 已支持 OpenAI 兼容 `chat/completions` 的单次非流式请求。
- `internal/diagnosis` 已提供初始 System Prompt 和用户故障描述消息。
- 当前输出可以包含 usage，但还没有会话对象和流式响应处理。

## 范围

### 必须完成

- 引入可追加的会话消息历史，至少支持 `system`、`user` 和 `assistant` 消息。
- 支持在同一进程中连续提交多轮用户输入，并将已完成的 assistant 回复加入历史。
- 支持流式增量读取并实时写入 CLI 输出。
- `context.Context` 取消后立即结束当前请求，并释放 HTTP 响应资源。
- 服务端断流、格式错误和 HTTP 错误返回可识别的错误。
- 失败、取消或断流时不写入不完整的 assistant 消息。
- 使用本地假服务覆盖正常流式、断流、取消和错误响应。

### 明确不做

- 不在本阶段实现自动重试、限流、熔断或多 Provider 路由。
- 不实现会话持久化、历史会话查询和跨进程恢复；这些属于 `M1-P03`。
- 不引入 RAG、Agent、MCP 或自动化生产环境操作。
- 不把流式输出强行解析为最终的结构化诊断 Schema；这属于 `v0.2`。

## 建议实现顺序

1. **抽象会话消息**：让单次调用和多轮调用复用同一组消息类型，明确 assistant 回复只有在完整成功后才能提交。
2. **实现流式客户端**：增加流式请求参数和 SSE/增量响应解析，逐块通过回调或返回的迭代接口交给上层。
3. **接入 CLI 多轮流程**：设计最小交互命令，支持提交补充信息，并区分正常结束、EOF、取消和失败。
4. **完善取消与资源释放**：确保请求、响应体、读取循环和输出协程都能在上下文取消后退出。
5. **补齐本地假服务测试**：验证请求消息顺序、增量输出、历史提交和失败回滚行为。

## 行为约定

- 用户消息发送前加入会话历史；assistant 消息只有在完整响应结束后加入历史。
- 流式过程中已经写到终端的内容不回滚，但内部会话历史不能保存这段不完整内容。
- `io.EOF` 表示服务端提前关闭连接时，若协议未发送完成标记，应视为断流错误，而不是成功响应。
- 上下文取消优先返回取消相关错误；调用方不得继续等待服务端完整响应。
- usage 如果在流式结束事件中提供则保留；未提供时继续使用 `Known=false`。

## 预计影响文件

- `internal/llm/client.go`：流式请求、增量事件解析和取消处理。
- `internal/llm/client_test.go`：流式客户端及异常场景测试。
- `internal/app/run.go`：多轮交互和流式输出编排。
- `internal/app/run_test.go`：CLI 会话行为和失败回滚测试。
- `internal/diagnosis/prompt.go`：必要时拆分初始消息和后续用户消息构造。
- `README.md`：补充 P02 运行方式和交互示例。
- `docs/evidence/`：补充正常流式、取消和断流证据。

## 验收清单

- [x] 可以提交第一轮故障描述并得到完整回复。
- [x] 可以继续提交补充信息，第二轮请求包含此前完整消息历史。
- [x] 流式模式下内容按增量写入输出，不等待完整响应才显示。
- [x] 取消流式请求后命令及时退出，且没有 goroutine 或 HTTP 资源泄漏。
- [x] 服务端断流时输出可理解错误，且下一轮不会携带半截 assistant 消息。
- [x] 服务端返回 HTTP 错误或非法流式数据时，错误能传递到 CLI。
- [x] `go test ./...` 通过。
- [x] `go vet ./...` 通过。
- [x] 相关验证记录写入 `docs/evidence/`。

只有当上述验收清单全部完成，并且正常、取消、断流和错误路径都有测试或证据后，才将 `M1-P02` 标记为完成，再进入 `M1-P03`。
