# ADR-0001：将 OpsPilot 作为课程持续实践项目

- 状态：接受
- 日期：2026-08-11

## 背景

课程已有 `ai-exp` 保存零散 Go 和 Python 实验，也有 notebook 知识库保存课程文章。仅靠实验无法展示知识如何组合成系统；把全部文章代码直接堆进一个项目，又会让教学实验和工程实现互相污染。

## 决策

OpsPilot 作为独立 Go 主项目，按课程模块逐步演进：

- `ai-exp` 负责隔离变量和快速验证；
- OpsPilot 负责稳定工程实现、测试、ADR、证据和版本；
- notebook 负责理论组织、实践叙事和公开文章；
- 三者通过学习单元 ID、代码路径和 Git tag 关联，不通过源码依赖强行绑定。

OpsPilot 第一版聚焦 Go HTTP 微服务故障诊断，默认只读，不自动执行生产变更。

## 原因

- 故障诊断天然需要多轮对话、流式输出、结构化结果、RAG、工具调用和审批，能承载课程主线。
- Go 与目标读者的后端开发背景一致。
- 单一持续项目可以展示架构演进和真实工程取舍。
- 实验与主项目分离后，Python 生态验证不会改变 Go 项目的技术边界。

## 后果

- 文章不能在代码和证据完成前宣称功能已实现。
- 每个里程碑需要同时维护代码验收和课程复盘。
- 有些纯理论或扩展知识不会进入 OpsPilot，需要继续使用独立实验。
- 项目会保留早期版本的限制，后续通过 tag 展示演进，而不是把历史重写成最终架构。
