> 服务器内存占用很高，cpu占用却不高
### 1. 现象摘要
- 服务器整体内存占用高，CPU 占用不高。
- 缺乏进一步细节，无法确定是 Go 进程本身的内存占用，还是其他进程 / 系统缓存占用。

### 2. 可能原因（标注不确定性）
以下为初步假设，均需证据验证：

- **Go 进程堆内存缓慢增长**：可能存在内存泄漏（如 goroutine 未退出、全局对象不断累积、`time.Ticker` 未释放等），导致 RSS 持续升高，但服务压力不大时 CPU 不高。可能性中等。
- **goroutine 泄漏**：大量 goroutine 阻塞或未被回收（如 channel 未关闭、互斥锁死锁、`select` 无超时），每个 goroutine 栈内存占用从 KB 到 MB 不等，累积后内存上升明显，而 CPU 可能不高。可能性中等。
- **存在无容量上限的全局缓存 / 对账数据累积**：如内存中保存了大量用户会话、任务队列、日志 buffer 等，且没有 LRU 或过期时间，导致内存只增不减。可能性中等。
- **连接池/对象池配置过大**：如数据库连接池、HTTP 连接池空闲连接太多，每个连接占用内存，但 CPU 使用低。可能性较低。
- **堆空闲内存未归还操作系统**：Go 的 GC 会将空闲堆内存保留在进程内（`runtime.MemStats` 中 `HeapIdle` / `HeapReleased` 可观察）。这可能导致 RSS 高，但实际可用。可能性中等。
- **误读指标**：`free` / `top` 显示的内存包括文件缓存（page cache），Linux 会尽量使用空闲内存做缓存，这在内存紧张时会被释放，不一定代表 Go 进程泄漏。可能性较高（需确认）。
- **使用了 CGO / 外部库**：通过 CGO 分配的内存在 Go GC 之外，不易复用，可能导致 RSS 持续上升，而 CPU 不高。可能性较低（需确认项目是否使用 CGO）。

### 3. 建议补充的证据
为了进一步定位，需要以下信息：

- **确认占用内存的进程具体是哪个**：`ps aux --sort=-%mem` 或 `top`，确认是否是目标 Go 服务。
- **Go 服务的基础监控指标**：
  - `go_runtime_memstats_heap_inuse_bytes` 或 `/debug/vars` 中的 `heap_inuse`
  - `go_runtime_memstats_heap_alloc_bytes`（当前堆分配按字节）
  - `go_runtime_memstats_heap_idle_bytes` / `heap_released`
  - `go_goroutines`（当前 goroutine 数）
  - `go_gc_duration_seconds` 或 `GOGC` 配置
  - 进程真实内存：RSS / VSZ 变化趋势
- **Go pprof 数据**：
  - `go tool pprof http://host:port/debug/pprof/heap` 采样的 `inuse_space` 和 `alloc_space` 对比
  - `go tool pprof http://host:port/debug/pprof/goroutine` 查看 goroutine 数量及调用栈
- **运行环境信息**：
  - 是否容器化（容器内存限制、cgroup）
  - 版本：Go 版本、依赖库版本
  - 最近是否有代码变更、依赖更新、发布历史
  - 服务运行时长：内存是从启动后一直涨，还是到达某个时间点后快速增长
- **业务特征**：请求类型、并发量、是否有大响应/大上传文件、定时任务等。

### 4. 下一步排查顺序

1. **确认内存归属**  
   使用 `ps` / `pmap` / `top` 确认到底是哪个进程的内存占用高。若与 Go 服务无关，检查系统服务或文件缓存。

2. **获取 Go 运行时基本指标**  
   如果确认是 Go 进程，优先查看：
   - `goroutine` 数量（若远大于活跃请求数，则存在泄漏）
   - `heap_inuse` 随时间变化
   - `heap_idle` 和 `heap_released`（确认是否为 GC 保留内存）

3. **抓取 pprof 堆和 goroutine 分析**  
   - 隔一段时间（如 5 分钟）抓两次堆 profile，观察增长对象类型。
   - 抓 goroutine profile，寻找 `waiting` / `blocked` 且数量持续增长的 goroutine。

4. **检查代码中可能的缓存/长生命周期对象**  
   关注包级别变量、全局 map/slice、单例对象、连接池配置，确认是否有清理机制。

5. **对比发布历史**  
   若内存问题是从最近一次发布后出现，重点检查变更内容（如新增缓存、长连接、协程未取消等）。

6. **实验性优化**  
   若确认是堆占用高且无泄漏，可尝试调整 `GOGC` 或 `GOMEMLIMIT`（Go 1.19+）限制内存；若确认是 goroutine 泄漏，修复泄漏点。

> 我是服务器是Linux，运行在docker中 
### 1. 现象摘要
- Linux 服务器上运行 Docker 容器，容器内进程（推测为 Go 服务）内存占用很高，但 CPU 不高。
- 具体是宿主机内存高还是容器内存高暂未明确，但大概率指容器内部（或容器在宿主中的占用）。

### 2. 可能原因（标注不确定性）
在 Docker 环境内，除了 Go 应用本身，还需考虑容器与宿主机的交互差异：

- **Go GC 未感知容器内存限制**（可能性较高）  
  Go 1.19 之前，`runtime` 读取的是宿主机 `/sys/fs/cgroup/memory/memory.limit_in_bytes`（或 cgroup v2 的 `memory.max`），若容器限制未正确暴露，Go 会按照宿主总内存来计算 GC 触发阈值（如 `GOGC=100` 时，堆
可增长到宿主内存的一半）。这会导致堆内存在容器限制下看起来很“高”，但 CPU 不高。即使 Go 1.19 至 1.21 增加了对 cgroup v2 的自动感知，但若容器运行方式特殊或版本较旧，仍可能存在问题。

- **进程内存泄漏 / goroutine 泄漏**（可能性中等）  
  与普通环境相同，但容器往往因内存上限较小，问题会被放大（更容易触发 OOM Kill）。

- **容器内页面缓存（page cache）造成误解**（可能性较高，尤其是 `docker stats` 或 `free` 直接输出）  
  容器内读取到的内存使用量可能包含内核页缓存，这部分可被回收。`docker stats` 默认显示的是容器 RSS + 缓存，而 `free` 在容器内看到的是宿主机的缓存总量，容易误判。

- **宿主机内存高但容器占用并不高**（可能性中等）  
  若只看 `top` 或宿主机 `free`，其他容器或进程也可能占用内存，需确认是否真的是当前 Go 服务容器造成。

- **CGO 分配内存不在 Go GC 管理内**（可能性较低，但需确认）  
  如果项目使用 CGO，C 层分配的内存在 `malloc` 中，没有 Go GC 参与，容器内的 RSS 会持续上涨且无法通过 Go heap 指标反映。

### 3. 建议补充的证据
需要同时从“容器层”和“Go 进程层”收集信息：

**容器层证据：**
- 容器内存限额：`docker inspect <container_id> | grep Memory` 查看 `Memory` 配置（0 表示无限制）。
- 容器实际内存使用：`docker stats --no-stream <container_id>`，关注 MEM USAGE / LIMIT。
- cgroup 统计（宿主机上执行）：
  ```bash
  cat /sys/fs/cgroup/memory/docker/<container_id>/memory.usage_in_bytes
  cat /sys/fs/cgroup/memory/docker/<container_id>/memory.limit_in_bytes
  # 若 cgroup v2：
  cat /sys/fs/cgroup/system.slice/docker-<container_id>.scope/memory.current
  cat /sys/fs/cgroup/system.slice/docker-<container_id>.scope/memory.max
  ```
- 容器是否被 OOM Kill：`dmesg | grep -i oom` 或 `docker inspect ... -f '{{.State.OOMKilled}}'`。

**Go 进程层证据：**
- 确认容器内的 Go 进程 PID，然后：
  ```bash
  cat /proc/<pid>/status | grep VmRSS    # 实际物理内存
  cat /proc/<pid>/smaps                  # 查看具体内存段
  ```
- Go 运行时指标（通过 `go tool pprof` 或暴露 `/debug/metrics`）：
  - `heap_alloc`、`heap_idle`、`heap_released`
  - `goroutines`
  - 系统内存统计：`runtime.MemStats.Sys`
- 环境变量中的 `GOMEMLIMIT`、`GOGC` 是否设置。
- Go 版本：`go version`，用于判断 cgroup 感知是否默认启用。

**其他：**
- 最近是否有代码发布、依赖更新（尤其是涉及并发、缓存、连接池的部分）。
- 服务运行时长、内存增长曲线（内存是持续上升还是到达某阈值后稳定）。

### 4. 下一步排查顺序

1. **先确认“高”是相对什么而言**  
   - `docker stats` 中容器的 MEM USAGE 是否接近 LIMIT？若 LIMIT 有值，计算使用比例。
   - 若未设置内存限制，看看宿主机的 `free -m` 与 `ps aux --sort=-%mem`，确认是否真的是本容器占用大量宿主内存。

2. **检查容器内部 /proc 数据**  
   - 进入容器，查看 `cat /proc/1/cgroup` 和 `cat /sys/fs/cgroup/memory.max`（或 v1）确认 cgroup 是否能被 Go 进程正确读取。
   - `cat /proc/<go_pid>/status | grep Vm{RSS,Swap}`，区分 RSS 是否包含共享库（如 libc）或其他分配。

3. **对比 Go 运行时指标**  
   - 确认 `heap_alloc` 是否接近容器限制？如果 `heap_alloc` 不大但 RSS 很大，重点排查 CGO/系统内存分配。
   - 查看 `heap_idle` 与 `heap_released`：如果 `heap_idle` 大且 `heap_released` 小，说明 Go 保留了空闲内存未归还 OS，可尝试设置 `GOMEMLIMIT` 或调整 `GOGC`。
   - 若 `goroutines` 数量高且活跃请求少，则为 goroutine 泄漏，抓 `goroutine` pprof。

4. **实验性措施快速缓解**  
   - 如果确认是 Go 堆空闲内存未释放，可在容器启动时设置环境变量：`GOMEMLIMIT=<容器内存70%>` 和 `GOGC=off` 或较低值（如 100），重新部署观察。
   - 若是 CGO 嫌疑，可通过 `strace -f -e trace=mmap,brk` 跟踪进程内存系统调用，或使用 `pmap` 查看进程地址空间分布。

5. **源码排查（按证据指向）**  
   - 若堆持续增长，用 `go tool pprof` 对比两次 heap profile，定位增长类型。
   - 若 goroutine 泄漏，分析 goroutine dump 中的阻塞等待位置（channel, mutex, time.Ticker 等）。
   - 若代码中有全局缓存、map，检查其清理机制。

6. **结合发布历史**  
   - 如果内存问题在最近一次发布后出现，重点审查新增的缓存、长连接、定时任务等代码。
