### 1. 现象摘要

- 现象：Go 服务 CPU 使用率突然升高，可能是进程 CPU 飙升，也可能是容器/主机层面观测到 CPU 升高。
- 当前信息量有限：未提供具体时间点、持续时间、服务类型、部署环境、日志、监控、代码变更等。

---

### 2. 可能原因（标注不确定性）

以下均为**可能性**，需要证据验证，不能直接认定为事实：

- **流量突增**（较常见）：请求量/QPS 上升，导致 CPU 正常升高。
  - 不确定性：不确定是否有流量峰值、是否存在异常流量。
- **代码热点或效率下降**：某条处理路径输入变化（如数据量增大、新参数组合）导致循环/排序/正则/序列化等耗时增加。
  - 不确定性：未确认是否有代码变更或输入特征变化。
- **死循环或忙等待**：某个 goroutine 陷入死循环、自旋或空转，造成 CPU 持续占用。
  - 不确定性：需要 goroutine 栈和 CPU profile 确认。
- **协程泄漏/无限增长**：大量 goroutine 被创建且未退出，调度和内存压力增加，进而拉高 CPU。
  - 不确定性：需要观察 goroutine 数量。
- **GC 压力增大**：内存分配频繁或堆内存增长，触发频繁 GC，CPU 被垃圾回收占用。
  - 不确定性：需要查看 GC 指标（如 `go_gc_duration_seconds`、`go_memstats_*`）。
- **锁竞争/并发瓶颈**：临界区竞争严重，导致大量 goroutine 自旋或上下文切换。
  - 不确定性：需要 mutex profile 或 block profile。
- **日志输出突增**：大量日志写盘，格式化日志本身可能消耗 CPU。
  - 不确定性：需要查日志量。
- **依赖服务或数据库变慢**：调用下游时反复重试、超时处理、连接池重建等导致 CPU 消耗。
  - 不确定性：需要确认下游访问耗时和错误率。
- **基础设施因素**：宿主机 CPU steal（虚拟化抢占）、同一宿主机其他容器干扰、CPU 配额变更。
  - 不确定性：需要宿主机/容器监控确认。
- **定时任务或后台批处理**：服务内部 cron/定时扫描启动，任务数据量变大。
  - 不确定性：需要确认是否有定时任务。

---

### 3. 建议补充的证据

为了定位问题，建议收集以下信息：

- **时间线**：
  - 升高具体时间点、持续时间、是否周期性。
  - 最近是否有发布、配置变更、流量活动、依赖变更。

- **进程 CPU 画像**：
  - 开启 pprof，采集 `profile`（CPU Profile）、`goroutine`、`heap`、`mutex`、`block`。
  - 注意：CPU Profile 建议在异常期间采集 30s 以上。

- **监控指标**：
  - 请求 QPS、P99 延迟、错误率（HTTP/自定义 RPC）。
  - goroutine 数量、GC 频率/耗时、堆内存、内存分配速率。
  - 进程 CPU 与系统 CPU 的区分（user vs sys）。
  - 容器 CPU 限额、宿主机负载、CPU steal 指标。
  - 磁盘 I/O、网络 I/O、日志写入量。

- **日志**：
  - 异常时间点前后日志，特别是 error/warn、panic、慢请求日志。
  - 下游依赖调用日志（数据库、Redis、外部 API）。

- **代码变更**：
  - 近期的 git 提交、配置文件变更、依赖库更新。

### 4. 下一步排查顺序

建议按顺序执行，避免盲目猜测：

1. **先确认现象范围**
   - 是单实例还是所有实例？确认是否与流量、发布、时间点有关。

2. **看变更与流量**
   - 检查最近有无发布、配置变更、下游变更；查 QPS 和延迟曲线，判断是否由请求量升高引起。

3. **抓取现场证据（关键步骤）**
   - 登录到 CPU 高的实例：
     - 执行 `go tool pprof http://localhost:<port>/debug/pprof/profile?seconds=30` 采集 CPU Profile。
     - 同时采集 `goroutine`：`curl http://localhost:<port>/debug/pprof/goroutine?debug=2 > goroutine.txt`
   - 如果服务没有开启 pprof，需要先通过内部机制临时开启（注意安全）。

4. **分析 CPU Profile 与 goroutine**
   - 用 `go tool pprof -top` 或 `-web` 查看热点函数，区分是业务代码、运行时（GC）、还是依赖库。
   - 检查 goroutine 数量是否异常增多，是否存在大量阻塞/死循环的 goroutine。

5. **观察运行时指标**
   - 查看 GC 指标和内存分配速率：`go tool pprof -top http://.../debug/pprof/heap`
   - 看 `go_gc_duration_seconds_sum` 增大速率是否很快。

6. **排除基础设施影响**
   - 如果进程本身 profile 无明显热点，检查宿主机 CPU steal、容器配额、其他容器争抢。

7. **结合日志与依赖**
   - 看异常时间点日志量、下游调用耗时/重试频率，判断是否有外部依赖拖累导致自旋或重试。

8. **临时降级/回滚验证**
   - 如果确认与最近变更相关，可考虑回滚或灰度，验证 CPU 是否恢复。
